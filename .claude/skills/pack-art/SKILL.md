# Pack art

The pack's art is made by agents, not generated by image models (charter;
remove this skill's work from the roadmap if the charter drops it). Pixel textures are written as data (a recolour recipe or a
text grid) and checked by eye; UI art is built from captures of the real game.
Every image in the pack is a **build output** of a source in `art/`.

Art direction (palette ramps, light, outline and shading rules, references)
is in `docs/design/art.md` and `art/palette.json`, owned by pack-designer.
If either is missing, return NEEDS_INPUT: don't invent a palette in a
texture brief.

## Where things go

| Source (tracked) | Builds to (ships) | What |
|---|---|---|
| `art/assets/<ns>/textures/item/<name>.{derive.json,grid}` | `packwiz/kubejs/assets/<ns>/textures/item/<name>.png` | item textures, 16x16 |
| `art/assets/<ns>/textures/block/<name>.{derive.json,grid}` | `.../textures/block/<name>.png` | block textures, 16x16, tile seamlessly |
| `art/assets/<ns>/textures/quests/<name>.compose.json` | `.../textures/quests/<name>.png` | chapter images (FTB Quests) |
| `art/assets/minecraft/textures/gui/title/background/panorama_<0-5>.png` | same path under `kubejs/assets/` | title panorama (studio capture, copied) |
| `art/captures/<name>.png` | nothing (input to `.compose.json`) | raw studio captures |
| `art/palette.json` | nothing | ramps and limits (designer) |

`<ns>` is the pack namespace (AGENTS.md → Conventions) for pack content. Overriding another mod's texture
means `art/assets/<modid>/...` and is a design decision (record it).
Animated textures: a `.grid` with `---` between frames and a `frametime`
line, or a derive from an animated base; the build writes the `.mcmeta`.

Formats (grid, derive ops, compose layers): [references/formats.md](references/formats.md).

## The tool

`python3 -I scripts/texture.py <cmd>` (full list: `--help`):

| Command | Use |
|---|---|
| `find '*copper*'` | find base and reference textures in vanilla, the roster's jars and the pack |
| `show <id> [--grid]` | colours dark to light; the grid to read a texture's structure |
| `ramp <id> [-n 5]` | sample a ramp (for the designer's palette) |
| `to-grid <ref> art/.../x.grid` | turn a texture or a derive result into an editable grid |
| `render <source> <scratch>.png` | try a source without touching the pack |
| `preview <ref>... --ref <neighbour>... --out <scratch>.png [--row] [--grey]` | the review sheet; **Read it**. `--ref A B` and repeated `--ref A --ref B` both work. Default: one block per texture, stacked. `--row`: the family layout, every texture and ref side by side as zoom over inventory slot, so a set reads at a glance. `--grey` for value checks (siblings must differ without hue) |
| `build [source...]` | write the pack PNGs (and `.mcmeta`) from `art/` |
| `lint` | sizes, alpha, colour counts, palette, stale builds, unsourced PNGs, startup registrations without a texture |
| `quantize <capture> <out> --size 32 --palette` | turn a render into palette pixel art |
| `panorama-check <dir> --out <scratch>.png` | six faces present, square, same size; seam sheet |

Write sources under `art/` with Write/Edit only: a hook blocks shell writes
there for subagents (no `cat >`, `tee`, `sed -i`, `cp`). Sources whose file
name starts with `_` (e.g. `_page.grid`) are helpers: they can be derive
bases but `build` never writes them to the pack. `lint` warns (not errors)
on a computed registration id or texture, such as a `forEach` loop with
`'<ns>:x_' + s`; check those textures by hand.

`scripts/check_pack.py` runs `lint`, so a deploy fails on a stale or
missing texture. Never edit a PNG under `packwiz/kubejs/assets/` by hand:
edit the source and `build`.

## Blocks and items: derive, then grid

### Tiers

Every row of the art inventory in `docs/design/art.md` has a tier, set by
the designer. The tier decides how far down the steps below a texture must
go:

| Tier | What | Must |
|---|---|---|
| **variant** | ordinary parts and materials: intermediates, residues, frames, building blocks | may stop at a derive (step 2), but with at least one visible change beyond colour (a detail, an inlay, an edge) so it isn't a pure recolour |
| **signature** | story and gate pieces the player is meant to remember: the key items of each act, the final craft, unique story artifacts | its **own silhouette**, drawn as a grid (step 3 or 4). Vanilla is a reference for shading, palette and pixel density, never the outline. A signature piece that reads as a recoloured vanilla item fails |

If the inventory gives no tier, treat the piece as signature and say so in
`defaults_taken`.

Each **family** (for example a set of gate items, a line of story notes, a
machine tier) has a shared motif in the art direction, for example the same
inlay on every gate item or the same rim on every seal. Every member carries
it, so the set reads as one pack-made family rather than as vanilla.

### Steps

For each texture, in this order. A variant stops at the first step that
passes the quality bar; a signature piece always reaches step 3 or 4.

1. **Find the base and the neighbours.** What does the object resemble
   in vanilla or the roster (`find`, `show`)? Pick a base with the right
   silhouette (variants) or the right material and shading (signature
   pieces), and 2-4 **neighbours**: the textures it will sit next to in an
   inventory or a wall (the materials it's made from, its tier siblings,
   its family).
2. **Derive.** A `.derive.json` that recolours the base onto a palette ramp
   (`ramp`), shifts it (`hsv`), swaps colours (`replace`), and layers detail
   (`overlay`, `mask`, `outline`). Layer parts from several textures if that
   gets closer. A variant can stop here once it has its non-colour change.
3. **Refine as a grid.** When the silhouette or details must change:
   `render` the derive, `to-grid` it into `art/.../<name>.grid`, delete the
   `.derive.json`, and edit the rows. Change a few pixels per round, not the
   whole grid. For a signature piece, redraw the outline first: if the result
   still has the base's outline, you're not done.
4. **Grid from scratch**, when no base is close (often the case for
   signature pieces). Block out the silhouette in two colours first, then
   the ramp shading, then highlights, then the family motif.

Each round: `render` (or `build`) → `preview <new> --ref <neighbours>` →
Read the sheet → write down what is wrong against the checklist below → fix.
Stop after ~4 rounds per texture. If it still fails, say so in `debt`
rather than polishing forever.

### Quality bar (16x16)

- **Silhouette reads at 1x** in the slot view: you can name the object.
- **Not a recolour.** Put the texture next to its base in the preview
  (`--ref <base>`). A player who knows vanilla shouldn't take it for the
  base in another colour. Variants need a visible non-colour change;
  signature pieces need their own outline.
- **Matches vanilla density.** Compare with the neighbours: similar size in
  the 16x16 frame, similar contrast, no smoother or noisier than vanilla.
- **Light from the top-left.** Highlights top-left, shadow bottom-right.
  No pillow shading (dark rim all round with a bright centre).
- **3-5 shades per material**, from one palette ramp. No gradients across
  the whole sprite, no stray single pixels of noise, no pure black or white
  unless the art direction says so.
- **Items:** transparent background, binary alpha, an outline from the
  darkest shade of the material (not black) where vanilla would have one.
- **Blocks:** opaque, tile seamlessly in the 3x3 view (no visible grid,
  no strong feature that repeats into a pattern unless intended), and read
  as the material from 5 blocks away (the "on dark" thumbnails).
- **Families agree.** Story items (gate items, story notes) share ramps
  and the family motif so the player sees a set, and each member is still
  told apart from its siblings at 1x. Check them side by side in one sheet.

### Licences

Vanilla textures are fine bases for this pack. A roster mod's texture is a
base only if its licence allows derivatives: check `license` in the jar's
`META-INF/neoforge.mods.toml` (`unzip -p <jar> META-INF/neoforge.mods.toml`)
or the Modrinth licence id from `scripts/mod_info.py <slug>`. For "All
Rights Reserved", use it as a reference, not a base. The source's `from`
records the base either way.

## Registered items and blocks

Every KubeJS startup registration names its texture explicitly:
`event.create('<ns>:<name>').texture('<ns>:item/<name>')`.
Blocks: `.texture('<ns>:block/<name>')` (all faces), or `.textures({...})`.
Until the art exists, the implementer points `.texture()` at a vanilla
placeholder (`minecraft:item/...`) and lists it in `debt`; `lint` fails on a
registration with no `.texture()` or a texture that doesn't exist. Block
items reuse the block model; give an item texture only if the design wants
a flat icon. After the art lands, switch the `.texture()` to the pack path
(a startup change, so it needs a restart).

## UI art: captures and composition

Chapter images, the title panorama and menu art are pictures of the game.
They come from the **studio** commands in the headless client (part of
the dev-only `pexp_devtools` mod): `/studio shot <name>` (a HUD-free frame
at the window size; launch the client with `PEXP_CLIENT_SIZE=1920x1080` or
similar for bigger shots), `/studio panorama <name> <size>` (the six
title-screen faces) and `/studio clean on|off`. Commands, replies, staging
and usage: [references/studio.md](references/studio.md). Transparent
cut-outs of entities, blocks and items are not built (future work; key out
a solid backdrop instead). MCPFabric `screenshot` (HUD included) is for
checking, not for art.

1. **Stage** (the brief must give you the runtime): a test area or the
   structure itself (`/locate`, `/tp`), `/time set`, `/weather clear`,
   `gamerule doDaylightCycle false`, spectator mode, bosses summoned with
   `{NoAI:1b,Silent:1b,PersistenceRequired:1b}`, then `/tick freeze` so
   nothing moves. Use the dev world; never stage near spawn or while the
   owner is online (`list_players`).
2. **Capture** with the studio commands (`mcf.py --client send_chat
   '{"message":"/studio shot <name>"}'`, reply via `get_recent_chat`).
   Read every PNG. Copy the keepers into
   `art/captures/` (or straight into the panorama path).
3. **Compose** a `.compose.json`: background, captures and textures as
   layers, darkened or desaturated so quest icons stay readable, optional
   `pixelate` and `quantize` to match the pixel look.
4. **Check in context.** Chapter images: `quests.py render <chapter>` shows
   them under the quest layout; then a real quest-book screenshot through
   the headless client. Panorama: `panorama-check`, then the title screen
   on the headless client after a restart.

FTB Quests chapter images (2101.1.37): each entry in a chapter's
`images: [...]` has `image` (texture id, e.g.
`<ns>:textures/quests/<name>.png`), `x`, `y` (centre, in quest-grid
units), `width`, `height`, `rotation`, `alpha` (0-255), `color`, `order`
(draw order; negative is behind the quests) and `dependency` (shown only
after that quest is done). The field names come from the jar's
`ChapterImage` class; confirm them against a chapter the mod has re-saved
before relying on any but `image`, `x`, `y`, `width` and `height`. Image
placement belongs to pack-quest-writer; the image file is yours.

Sizes: chapter images 256-512 px on the long side; panorama faces 1024 px;
keep the pack small.

## Taste is the owner's

Visual taste is owner-reserved (charter). When a set of art is done (a
family of textures, a chapter's images, the title screen), queue one
human-test request in `docs/human-testing/queue.md` with the preview sheets
and what to look for, through the orchestrator. Don't block on it.

## Before you return

- `python3 -I scripts/texture.py build` then `lint` (0 errors).
- `python3 -I scripts/check_pack.py`; `quests.py check` if chapter images
  changed.
- Preview sheets saved under `.claude/scratch/<task>/`, named in `checks`.
- In-game screenshot paths if you had the runtime; otherwise list the
  in-game checks for pack-tester in `debt`.
